# Question selection, reports, moderation, and measurements

The default selection mode reserves unseen question identities when a session starts, including questions not answered before leaving. The ledger is separate from the 50-entry result history and lives in this browser's localStorage. The existing history and restored session seed older known draws when the ledger is first created. It is not private-library cloud sync. For 400 questions and draws of 60, six sessions have 60 unique questions each and the seventh has 40. Exhaustion disables starting until the user explicitly resets the selected pool or chooses random selection. Reset affects only the selected source/subject; options retain their original order. Source versions distinguish revised material. The browser Web Locks API serializes starts across tabs where available, and each selection refreshes stored progress. Session-save failure rolls back the reserved ledger where storage permits. Browser clearing removes this ledger.

After study grading, each question has a report button. Library and submitted-result questions also provide reports. An image-load failure allows a report before grading, with the answer/explanation redacted; mock exams never expose answer keys through reports. Submitting explicitly discloses that the question, visible answer/explanation, and the user's message are sent to review. Private Google source links/images, Google identity and study answers are not collected. Public-deck references allow reviewers to compare the original slide. Anonymous reports are capped at five per minute and thirty per day per daily hashed network identifier. Reports never publish cache edits.

Only the server-configured verified Google email allowlist can list reports, see aggregate measurements, or replace/invalidate shared explanations. Google OAuth audience, expiry and identity are verified. The configured reviewer is injected from the repository variable `MODERATOR_EMAILS`; it is never a visitor-editable setting. Report status and cache edits use optimistic revisions. Reviewers can correct the answer/reasons while preserving original option labels and text, or invalidate a cache entry for regeneration. This does not silently rewrite speaker/manual answer keys. Resolving an answer/image report records a review note; correcting the original published deck still requires publishing a corrected source. Logging out or switching account closes review dialogs.

Structured explanations now include a shared-cache identity/revision. Saved explanations are checked when used (at most once per identity/revision per five minutes per page). A changed/revoked revision drops stale local/embedded explanations and retrieves the corrected or regenerated result. Offline readers retain their last local copy until a check succeeds. Older local explanation keys are upgraded once to include this metadata. In-flight generation is not persisted over a concurrent moderator edit.

Measurements contain only whitelisted event names, bounded milliseconds, and mobile/desktop classification: image attempts/errors, AI latency/errors, shared cache hits/misses, unique local cache reuse, JavaScript errors and unhandled rejections. No question text, URL, stack, email or token is sent. Failed uploads are dropped rather than blocking study. Aggregates show sample counts, mean durations and approximate P95 upper bounds from duration buckets; client data is advisory and can be forged. The dashboard shows fourteen days. Old aggregates and daily hashed rate identifiers are removed by alarm; report content stays in the private review queue until handled. API access is guarded independently of UI visibility.

Validation: 155 Node tests and static/module syntax checks. The isolated `outputs/quality-qa` Chrome profile (port 9224) exercises all seven draws, exhaustion, random selection, reset, guest reporting, authorized manual correction, stale browser cache replacement without another model call, anonymous metrics, logout protection, and twenty light/dark desktop/mobile/landscape selection/report/measurement layouts. Services use the actual Worker/Durable Object implementation with synthetic Google/Gemini responses; no real user data is cleared. Production smoke checks use invalid report input and an empty measurement batch, never a real-user report, and verify moderation reads are forbidden to guests. A real reviewer login cannot be exercised without the user's token.
